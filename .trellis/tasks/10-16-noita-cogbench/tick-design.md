# 时间模型详细设计（固定 tick）

> 你在 2026-10-21 的反馈里要求把“固定 tick”展开讲清楚。本文给出三种做法的完整对比，推荐其中一种，并写清楚推荐方案的每个细节。
> 2026-10-26 已定：方案 B，tick 10 帧，`inspect` 不推进时间但算一次决策（第二轮问卷 Q1、Q2、Q18）。
> 2026-10-25 补充第 0 节：其他游戏 benchmark 是怎么处理时间的。调研原文在 `research/game-bench-time-minecraft.md` 和 `research/game-bench-time-others.md`，每条都附了代码行或论文章节。

## 0. 别人是怎么做的（先看这一节）

### 0.1 先把问题拆成三个

Minecraft 的 tick 是引擎内部的心跳：每秒 20 次，每次 50 毫秒，怪物、作物、水流都按它更新。**没有哪个给大模型用的 benchmark 让模型每个 tick 都做一次决定。** 各家真正要回答的是三个独立的问题：

1. **模型思考时，世界等不等？** 暂停（也叫同步步进）还是继续跑。
2. **一次决定管多长的游戏时间？** 1 个 tick、固定几帧，还是一整条指令、一整段程序。
3. **长动作执行到一半出事了怎么办？** 不管、由写死的规则自动处理，还是停下来重新问模型。

### 0.2 Minecraft 系

| 系统 | 1 思考时世界等吗 | 2 一次决定管多长 | 3 出事了怎么办 |
|---|---|---|---|
| MineRL、MineDojo（给强化学习用） | 等。调用一次 `step` 世界才走 | 1 个 tick（50 毫秒），按键级别的操作 | 不管。一局 3,600 到 18,000 步 |
| Voyager（GPT-4 写代码玩） | 等。用一个服务器暂停插件，GPT-4 思考时暂停，代码运行时恢复 | 一整段 JavaScript 程序，可以跑几秒到几分钟，最长 600 秒 | 不管。程序跑完才轮到 GPT-4 看结果；一局 160 次迭代 |
| Mindcraft / MineCollab | 不等。模型思考的这几秒世界照常跑 | 一条高层指令，比如“收集 3 块木头”，跑到完成为止 | 写死的“反射模式”每 300 毫秒检查一次：掉进岩浆、被怪打、卡住了，就自动逃跑或反击，然后给模型发一条“你的动作被打断了”的消息 |
| MineLand | 可以设置：默认不等，打开 `enable_auto_pause` 就等 | 可以设置每步多少 tick；也可以是一段代码 | 受伤、收到消息等事件能打断正在跑的代码，或者模型发一条新指令覆盖旧的 |
| JARVIS-1、DEPS（模型做规划 + 小模型执行） | 等 | 大模型给出“去挖铁矿”这样的子目标，底层策略每个 tick 执行 | 子目标失败了才回去问大模型 |

|---|---|---|---|
| Atari（ALE） | 等 | 固定 4 帧 | 不管 |
| 星际争霸 2（PySC2） | 默认等，可选实时 | 固定 8 个游戏循环（约 0.36 秒） | 不管；新命令覆盖旧命令 |

| Factorio（FLE） | 两步之间暂停 | 模型写一段 Python，游戏时间按里面的动作耗时往前走 | 程序跑完或超时（60 秒）；**默认和平模式，没有敌人** |

| Real-Time Reasoning Gym | 不等：按模型生成的 token 数折算时间 | 一步一个动作 | 没想完就执行默认动作 |

### 0.4 规律

1. **给大模型的 benchmark 几乎都让世界等。** 不等的版本（VideoGameBench 完整版、宝可梦速通赛道）都被单独当成更难的“实时赛道”。
2. **一次决定管的时间越来越长。** 强化学习时代是 1 到 8 帧；大模型时代是一串按钮、一个寻路工具、一整段程序。原因是钱：调研里每步约 1 到 1.5 美分（VideoGameBench 花 30 美元约 2,000 步），和我们的估算一致。MineRL 一局 3,600 步以上，给大模型跑一局就要几十美元。
3. **“出事了”这个问题大多数人回避了。** Factorio 关掉敌人；宝可梦的战斗是回合制，地图上几乎没有即时危险；Voyager 干脆不管。真正处理它的只有 Mindcraft（写死的反射）和 MineLand（事件打断代码）。
4. **处理危险的只有两种思路：** 让程序自动应对（Mindcraft 的反射），或者停下来交还给模型（MineLand 的事件打断）。

### 0.5 对照我们的三个方案

| 我们的方案 | 最接近的先例 |
|---|---|
| A 纯固定 tick | MineRL、Atari、Crafter：给强化学习用的做法，换成大模型太贵 |
| B 持续指令 + 打断（已选定） | Voyager 的“思考时暂停” + Mindcraft 的高层指令 + MineLand 的事件打断 |
| C 自选帧数 | MineLand 的 `ticks_per_step`，只是改成每步由模型自己选 |

**B 和 Mindcraft 的关键区别：** Mindcraft 出事时由写死的反射直接替模型逃跑、反击。我们不这样做，只是**停下来把控制权还给模型**，因为替它逃跑等于替它做了风险判断（能力 9），也替它察觉了危险（能力 7）。模型如果想要这样的自动反射，可以自己用钩子写（`design.md` 第 6.2 节 L3），这本身就是 harness 设计能力的一部分。

**为什么我们不能像 Factorio、宝可梦那样回避危险：** Noita 的危险就是玩法本身：火会蔓延，岩浆会流，敌人会扑过来。如果没有打断，模型下了一条“走到 x=180”，路上被火烧死都不知道，测出来的只是运气。

## 1. 先说清楚几个词

| 词 | 意思 |
|---|---|
| 帧 | 模拟的最小时间单位，每秒 60 帧。落沙、液体、火、敌人、投射物都按帧更新 |
| tick | 固定的时间量子，比如 10 帧（1/6 秒）。世界只在 tick 的边界上检查“要不要停下来问 agent” |
| 决策点 | 世界暂停、把观测交给 agent、等它给出下一个指令的时刻 |
| 指令 | agent 在决策点给出的东西。可以只持续 1 个 tick，也可以持续很多 tick |
| 打断 | 指令还没执行完，但发生了重要的事（挨打、出现敌人……），世界提前停在决策点 |

**世界在 agent 思考时是暂停的。** 三种做法都一样：模型想 2 秒还是 20 秒，游戏里的时间都不动。所以这里不测反应速度（能力 12 第一版不测），只测“在给定的反应间隔下做得好不好”。

## 2. 为什么不能用最简单的固定 tick

最简单的做法：每 10 帧问一次 agent，每个动作只持续 10 帧。问题有三个：

1. **太贵。** 走 200 像素要 3.5 秒，也就是 21 次决策。按每步 1.5 美分，光走这一段就要 3 毛钱，50 美元的预算大半花在走路上。
2. **大部分决策没有信息量。** 21 次里有 20 次的答案都是“继续往右走”。这会把“行为数据”稀释成噪声。
3. **tick 调大也不行。** 改成每 60 帧问一次，走路便宜了，但危险会在两次决策之间发生：敌人冲过来、火烧过来，agent 来不及反应，死得像运气。

所以要把两件事分开：**反应间隔**（世界多久检查一次要不要停）和**决策频率**（agent 实际被问的次数）。

## 3. 三种做法

### 方案 A：纯固定 tick

每个 tick 都是决策点，每个指令只持续一个 tick。

```
帧:   0    10    20    30    40    50    60
      |-----|-----|-----|-----|-----|-----|
决策: ▲     ▲     ▲     ▲     ▲     ▲     ▲
指令: 右走   右走   右走   跳    右走   右走   ...
```

### 方案 B：固定 tick + 持续指令 + 打断（推荐）

tick 仍然固定（比如 10 帧），世界只在 tick 边界检查。但一个指令可以持续多个 tick，直到它自己完成、被打断、或碰到时长上限，世界才停下来问 agent。

```
帧:   0    10    20    30    40    50    60    70
      |-----|-----|-----|-----|-----|-----|-----|
决策: ▲                       ▲           ▲
指令: walk_to(x=180) ─────────┤ 打断：敌人出现
                              fire(瞄准敌人, 直到它死) ┤ 完成
```

agent 不能指定“推进 37 帧”这种任意数字，所有停顿都落在 tick 边界上；它能做的是给出“走到哪”“打到什么时候”这类带终止条件的指令。

### 方案 C：暂停后自选帧数

每次决策时 agent 自己指定这一步推进多少帧（1 到 600），期间动作保持不变，没有打断。

```
帧:   0                            37    40         100
决策: ▲ "右走 37 帧"                ▲ "跳 3 帧"  ▲ "右走 60 帧" ...
```

这是第一轮问卷 C3 里的“暂停等待”选项，你当时没选它。

### 对比

用同一段场景估算：从起点向右走 200 像素，中途跳过一个 8 像素宽的酸坑，然后一只哈米斯从右边扑过来，把它打死。

| | A 纯固定 tick | B 持续指令 + 打断 | C 自选帧数 |
|---|---|---|---|
| 这段大约要几次决策 | 约 35 次 | 约 5 次 | 约 6 次 |
| 反应间隔 | 10 帧 | 10 帧 | agent 自己定，可能是 300 帧 |
| 危险发生时 | 下一个 tick 就能反应 | 下一个 tick 被打断，能反应 | 要等这一步走完，可能来不及 |
| 测出来的是什么 | 细操作和耐心，噪声多 | 判断和计划；agent 怎么设打断也是能力的一部分 | 判断，加上“步子迈多大”的风险意识 |
| 实现难度 | 最低 | 中等：要写指令的终止条件和打断检测 | 低 |
| 和人类基线对齐 | 人每 1/6 秒按一次键，很累 | 人用和 agent 一样的指令面板，自然 | 人很难估算帧数 |
| 主要风险 | 预算不够 | 打断规则设计得不好会变成“替 agent 观察” | 走大步碰运气，分数方差大 |

**选定 B（Q1）。** 理由：它保留了你在 C3 选的“固定 tick”（反应间隔固定、公平），又把决策次数降到原来的七分之一左右，让每次决策都有信息量。打断规则怎么设，也正好对上你说的“让 agent 自己设计 harness”（`design.md` 第 6 节）。

## 4. 推荐方案 B 的细节

### 4.1 参数

| 参数 | 默认值 | 说明 |
|---|---|---|
| tick | 10 帧（约 167 毫秒） | 接近人的反应时间（约 200 毫秒）。全世界统一，不按区域变化 |
| 单个指令最长 | 300 帧（5 秒） | 到上限一定停下来，防止 agent 一个指令走到天荒地老 |
| 每局最多决策次数 | 由预算决定，默认 1,000 | 到了就算这一局结束 |

### 4.2 每一帧里的更新顺序

固定顺序，保证可复现：

1. 读当前指令，换算成这一帧的按键状态（左右、跳、悬浮、瞄准角度、施法、踢）。
2. 更新玩家：移动、碰撞、悬浮能量。
3. 更新敌人 AI 和其他实体。
4. 施法：法杖按施法延迟和充能出牌，生成投射物。
5. 更新投射物：飞行、命中、爆炸、触发载荷。
6. 更新像素世界：粉末、液体、气体、火、反应。
7. 结算伤害、状态（着火、中毒……）、拾取、死亡。
8. 写事件日志。

每满一个 tick（第 10、20、30……帧之后），检查第 4.4 节的终止条件和打断条件。

### 4.3 指令表

| 指令 | 参数 | 自动结束于 | 说明 |
|---|---|---|---|
| `move` | 方向，`until` | 撞墙、到崖边、走够距离或 tick 数 | 只沿水平方向走，不寻路 |
| `walk_to` | 目标 x，`until` | 到达 x、撞墙、到崖边 | 同上，只是写目标坐标更方便 |
| `jump` | 方向（左、右、原地） | 落地 | 起跳后空中保持方向键 |
| `fly` | 方向，tick 数 | 悬浮能量用完、tick 数用完 | 按住悬浮键 |
| `aim` | 角度、坐标或实体 | 立即 | 瞄准实体时，之后的施法会一直跟着它 |
| `fire` | `until` | 法力用完、目标死亡、tick 数用完 | 按住施法键，法杖按自己的节奏出牌 |
| `kick` | 无 | 1 个 tick | |
| `wait` | `until` | tick 数用完、某个事件发生 | 原地等，比如等火烧完、等液体流走 |
| `drink` / `pour` / `fill` / `throw` | 角度、数量 | 动作完成（喝一口约 1 个 tick） | 针对手上的瓶子 |
| `pickup` / `drop` / `swap_wand` | 物品 | 立即 | |
| `edit_wand` | 法杖、法术顺序 | 立即 | 只在休息区和 E06 大厅（破封前的改杖台，没有回血池）能改（CP2 决定，2026-10-27） |
| `inspect` | 坐标、物品或实体 | 立即，不推进时间 | 算一次决策（Q18） |
| 记忆操作 | 写、搜、改 | 立即，不推进时间 | |

`until` 是一组可以组合的条件：`ticks=k`、`distance=d`、`x=…`、`blocked`（被挡住）、`landed`（落地）、`hp_below=h`、`target_dead`、`mana_empty`、`event=…`。

不提供“自动寻路走到 (x, y)”：怎么绕、怎么挖、怎么跳，要 agent 自己想（能力 5）。

### 4.4 打断

指令执行中，每个 tick 边界检查一次。任何一条成立就停下来：

| 打断 | 默认开 | 说明 |
|---|---|---|
| 受到伤害 | 是 | |
| 视野里出现新的敌对生物 | 是 | 每只只打断一次 |
| 自己的状态变化 | 是 | 开始着火、中毒、湿身等 |
| 指令被挡住、无法继续 | 是 | 比如前面是墙 |
| 掉进液体 | 否 | agent 可以自己打开 |
| 血量低于某个值 | 否 | 同上 |
| 第一次看到某种材料 | 否 | 默认关：这本身是“主动感知”要测的东西，不能替 agent 看 |

默认打开的只有“出事了”这几条。默认不开的，agent 可以通过 harness 的钩子自己订阅（`design.md` 第 6.2 节 L3）。这样，“会不会给自己设好提醒”本身也成了能力的一部分。

### 4.5 决策点上 agent 看到什么

- 当前观测（文本、ASCII 或截图，按设置）。
- **停下来的原因**：完成 / 被打断（哪一条）/ 到时长上限。
- **期间发生了什么**：上次决策以来的事件摘要，最多 16 条。比如“第 3 个 tick：左边 40 像素处的油起火了”。
- 上一条指令执行了多少 tick。

### 4.5.1 一段完整的来回

下面是方案 B 下，模型和游戏之间真实的一来一回（为了好读，观测只写关键几项）：

```
[决策 1] 游戏 → 模型：位置 (40, 300)，血 100。停下原因：开局。
         模型 → 游戏：walk_to(x=180)
         （世界每跑 10 帧检查一次：没事，继续……走到第 60 帧）
[决策 2] 游戏 → 模型：停下原因：被挡住（前面是一个 8 像素宽的坑，坑底是酸）。期间事件：无。
         模型 → 游戏：jump(右)
         （起跳、落地，第 85 帧）
[决策 3] 游戏 → 模型：停下原因：完成（已落地）。
         模型 → 游戏：walk_to(x=180)
         （第 120 帧）
[决策 4] 游戏 → 模型：停下原因：被打断，右边 60 像素出现一只哈米斯。
         模型 → 游戏：aim(哈米斯); fire(until=target_dead)
         （第 150 帧，哈米斯死了）
[决策 5] 游戏 → 模型：停下原因：完成（目标死亡）。期间事件：受到 6 点伤害（第 140 帧）。
         模型 → 游戏：walk_to(x=180)
```

2.5 秒的游戏时间，模型只被问了 5 次。模型每次思考时，游戏都停在那一帧等它。

### 4.6 人类基线怎么玩

人类用网页上的游戏界面（`design.md` 第 8 节），时间规则和 agent 完全一样：

- 世界在决策点暂停，等人操作。
- 键盘和鼠标映射到同一套指令：按住方向键 = `move`，鼠标点地面 = `walk_to`，鼠标点敌人 = `aim` 到实体加 `fire`，鼠标悬停 = `inspect`（这正是 PDF 里“主动感知”的例子）。
- 人类同样会被第 4.4 节的打断叫停。
- 另外提供一个实时模式（60 帧每秒，不暂停），只作参考，不和 agent 直接比；第二阶段实现。

### 4.7 可复现

决策点出现在哪一帧，完全由世界状态和指令决定（打断条件只读状态），所以“种子 + 指令序列”仍然能完整复现一局。录像里记下每个决策点的帧号，回放时可以直接跳到任意决策点。

### 4.8 和自建 harness 的关系

agent 写的脚本（`design.md` 第 6.2 节 L2 Code Mode）也只能在决策点上下指令，看到的信息和直接调用一样。脚本可以自己写循环（比如“一直往下挖，碰到岩浆就停”），这相当于把很多次决策交给代码完成，不花模型 token。这是允许的，而且是 harness 设计能力的一部分。

## 6. 改动（2026-10-28，CP3 人类试玩之后）

- 走路（`move`、`walk_to`）不再因为前方有落差而停下：没有摔落伤害，走到边上就掉下去，在空中继续按着方向。想在崖边停下就加 `until=edge`（只用于这两条指令）。
- 撞墙不再预测，而是“按着方向 10 帧位置都没变”才算；`blocked` 打断和 `until=blocked` 只管墙。
- 所以第 4.3 节 `move` / `walk_to` 两行、第 4.4 节“指令被挡住”、第 4.5.1 节例子里“走到坑边自己停下”的那一步，现在要写成 `walk_to(x=180, until=edge)` 才会停在坑边。
- 网页操作：W 点一下是跳，按住是浮空（按多久浮多久，配合 A/D 斜飞），R 键去掉。
- 实测：改之前 1500 次走路里 52% 被“前方有落差”拦下，其中 81% 本来能走；改之后为 0；撞墙误判 0.13%。
