# Research: How non-Minecraft game benchmarks and LLM game-playing systems relate game time to agent decisions

- **Query**: For ALE, PySC2/SC2LE, TextStarCraft2, OpenAI Five, VideoGameBench (+Lite), BALROG, Factorio Learning Environment, Claude/Gemini Plays Pokemon, Cradle (plus Orak, Real-Time Reasoning Gym, PokeAgent speedrunning, Street Fighter latency work, Balatro): is the clock paused or real time, how many frames/steps per agent action, what is the action granularity, how do actions end or get interrupted, how many decisions per episode, and what is the cost?
- **Scope**: external (arXiv papers, official docs, actual repo source files). Minecraft is covered by a separate file (`game-bench-time-minecraft.md`).
- **Date**: 2026-10-25
- **Evidence tags**: `[paper]` = read in the paper PDF text; `[code]` = read in repo source (default branch on 2026-10-25, file + line numbers of the fetched raw file, can drift); `[docs]` = official docs page; `[secondary]` = blog/forum/third-party paper describing a system (flagged where it is the only source); `[derived]` = my arithmetic from cited numbers; `UNVERIFIED` = could not confirm.
- **Method note**: papers were fetched as PDFs through arXiv and converted with `pdftotext`; repo files were fetched from `raw.githubusercontent.com` / `gh api`; web pages were opened with ego-browser (TaskSpace 5). Local copies are in the session scratchpad only, not in the repo.

## 0. Pattern summary

1. **Almost every LLM game benchmark is lock-step: the world only advances when the harness advances it.** ALE, PySC2 (default), TextStarCraft2 (default), BALROG, VideoGameBench Lite, FLE (between steps), the "X Plays Pokemon" harnesses, Orak (main eval) and Cradle (for RDR2/Stardew) all freeze the game while the model thinks. Real-time-while-thinking exists but is a minority and is usually labelled a harder, separate track (VideoGameBench full, Orak SC2 real-time, PokeAgent speedrunning, Street Fighter/FPX, Real-Time Reasoning Gym).
2. **The unit of time is a fixed quantum of game frames per decision.** RL-era systems use 4 (ALE v5, OpenAI Five, python-sc2 default), 5 (Machado baselines), 8 (PySC2 default `step_mul`). LLM-era systems use 15-30 frames per button (VideoGameBench Game Boy), 130 frames per button (Claude Pokemon starter), 4 frames for a "Mario step" (Orak), or variable-length high-level actions.
3. **LLM harnesses raise the action level to cut cost and boost signal**: lists of buttons per call (VideoGameBench, Pokemon), A*-based `navigate_to` tools (Claude/PokeAgent), named macro-actions with rule-code behind them (TextStarCraft2, Orak SF3/SC2), model-written Python programs (FLE), model-written skill functions with a duration argument (Cradle).
4. **Interruption is rare and is mostly implemented outside the LLM.** No lock-step system lets a running action be pre-empted by an event mid-action (the only exceptions found: Cradle composite skills that break on an OCR/text change, and OpenAI Five/Orak SF3 where a new action simply overrides at the next decision point). Dangers are handled by (a) short fixed quanta, (b) rule-code defaults (TextStarCraft2 `defend()`, `distribute_workers()`), (c) observation flags (PySC2 `Alerts`), or (d) default-action fallbacks (Real-Time Reasoning Gym).
5. **"Thinking costs game time" is implemented in four different ways**: real wall-clock time with a free-running emulator (VideoGameBench full, PokeAgent speedrunning, Street Fighter/FPX), a one-step action offset (OpenAI Five), token count as a proxy for time (Real-Time Reasoning Gym: world steps every T_E generated tokens), and a bounded pause window (Cradle's ESC pause with a 0.5 s animation during which the world still moves).
6. **Decision counts and cost**: ~1k-5k LLM calls per run is typical (VideoGameBench ~2,000 steps for $30 cap, FLE 128 calls per lab task / 5,000 per open-play run, Cradle 30-1,000 steps per task, Orak 100-10,000 steps). Reported per-step cost is about 1-1.5 US cents for frontier VLMs (VideoGameBench: $30 ~ 2,000 steps; FLE: roughly 1.3 cents per step for Claude 3.5 Sonnet by dividing Table 3 by 8 x 5,000 steps, derived and approximate).

## 1. Arcade Learning Environment (Atari)

**Sources**: Machado et al. 2018, *Revisiting the ALE: Evaluation Protocols and Open Problems for General Agents*, JAIR, https://arxiv.org/abs/1709.06009 (Sec. 2.1 "Frame skipping", Sec. 5.2 "Sticky Actions" incl. its closing discussion of alternatives, Table 5 hyper-parameters); ALE/Gymnasium docs https://ale.farama.org/environments/ ("Stochasticity" paragraph + the version table).

1. **Clock**: synchronous. The emulator is deterministic and advances only when the agent submits an action; a frame is 1/60 s [paper Sec. 2.1: "A frame (as a unit of time) corresponds to 1/60th of a second ... The ALE is deterministic: given a particular emulator state s and a joystick input a there is a unique resulting next state s'"]. The paper lists "asynchronous environment" (Minecraft/Malmo, SC2, robotics) only as an *alternative* it does not use [paper, end of Sec. 5.2, "alternatives to sticky actions"]. Frames per agent step: frame skip k repeats the chosen action for k consecutive frames; "values of k = 4 and k = 5 have been commonly used" [paper Sec. 2.1]. Machado's own baselines use frame skip 5, episode cap 18,000 frames = 5 minutes [paper Table 5]. Current Gymnasium `ALE/*-v5` defaults: `frameskip=4`, `repeat_action_probability=0.25`; the older `*NoFrameskip-v4` has `frameskip=1`, sticky 0.0 [docs version table]. A tuple `frameskip=(a,b)` gives stochastic skipping [docs].
2. **Action granularity**: one low-level joystick input (direction + optional fire), held for k frames. Sticky actions: each frame there is probability varsigma=0.25 that the emulator repeats the *previous* action instead of the new one, so the realised delay follows a geometric distribution; unlike random delays, the agent may change its mind at any step [paper Sec. 5.2]. The paper explicitly contrasts this with "random frame skips" (agent cannot react inside the skip, has perfect reaction time otherwise) [paper, end of Sec. 5.2].
3. **Duration / interruption**: every action lasts exactly k frames; the agent cannot react to anything inside the skip window (paper: frame skip "restricts the agent's decision points"). No concept of dangers or pre-emption; sticky actions are the only injected timing noise.
4. **Decisions / cost**: with the paper's settings, 18,000 frames / frame skip 5 = 3,600 decisions per 5-minute episode [derived]. Cost: not applicable (RL). Larger caps in newer protocols: UNVERIFIED here.

## 2. PySC2 / SC2LE

**Sources**: Vinyals et al. 2017, *StarCraft II: A New Challenge for RL*, https://arxiv.org/abs/1708.04782 (Sec. 3.5/3.6); PySC2 source https://github.com/google-deepmind/pysc2 : `pysc2/env/sc2_env.py` (lines 106-107 `step_mul`, `realtime=False`; 149-158 docstring; 457-471 `action_delays`; 507-558 `step`/`_step`), `pysc2/maps/lib.py:66` (`step_mul = 8`), `pysc2/lib/features.py:538-541` (`action_delay_fn`), `docs/environment.md` ("Game and Action Speed", `step_mul` paragraph, `Alerts`).

1. **Clock**: two modes.
   - **Default `realtime=False` = lock-step**. "Acting through an API allows you to control the clock ... you can step as fast or as slow as you want ... This also means there is never any lag" [docs/environment.md]. The SC2 engine simulates 16 (normal) or 22.4 (fast) game loops per second [paper Sec. 3.5]. `step_mul` = "How many game steps per agent step"; map default is 8 (`maps/lib.py:66`); the paper acts "every 8 game frames, equivalent to about 180 APM" [paper Sec. 3.5]; docs example: `step_mul`=16 = 1 s of game time. Acting less often "reduces the compute, but diminishing returns kicks in fairly quickly ... little gain above 8 steps per action" [paper Sec. 3.6].
   - **`realtime=True`**: "the game simulation automatically advances (at 22.4 gameloops per second) rather than being stepped manually. The number of game loops advanced with each call to step() won't necessarily match the step_mul ... Game loops will be skipped if they cannot be retrieved and processed quickly enough" [`sc2_env.py:152-158`]. Observation-to-action delay is then logged in `action_delays()` (`sc2_env.py:457`). In lock-step mode an optional `action_delay_fn` can inject a random game-loop delay per action to simulate latency (`features.py:538-541`).
2. **Action granularity**: a human-like UI action = function id + typed args (`Move_screen(queued, screen_xy)`, `Attack_minimap`, `select_rect`, `build_queue`, ...), ~300 function ids [paper Sec. 3.5; docs]. Orders then persist inside the SC2 engine across many game loops (units keep walking/attacking after the call). A `queued` boolean argument implements shift-queueing [docs action list].
3. **Duration / interruption**: the agent is re-queried every `step_mul` loops regardless of what units are doing; issuing a new order overrides the old one (or appends if `queued`). There is no harness-level interruption; the observation has an `Alerts` tensor "for when you're being attacked in a major way" [docs, `Alerts`] but nothing stops a step early.
4. **Decisions / cost**: no per-game agent-step count is reported in the paper; a 30-minute game at 22.4 loops/s with `step_mul`=8 would be ~5,000 agent steps [derived, illustrative only]. Training used 600M agent steps (8 x 600M game steps) [paper Sec. 5]. Throughput 200-700 game steps per wall-second single-threaded at 8 frames/action on ladder maps [paper Sec. 3.6].

## 3. TextStarCraft2 (LLM plays StarCraft II, "Chain of Summarization")

**Sources**: Ma et al. 2023/24, *Large Language Models Play StarCraft II: Benchmarks and A Chain of Summarization Approach*, https://arxiv.org/abs/2312.11865 (Sec. 4, Algorithm 1, Sec. 5.3). Code (fork matching the paper; see Caveats on the original repo): https://github.com/sc2musa/Large-Language-Models-play-StarCraftII , files `sc2_rl_agent/starcraftenv_test/agent/chatgpt_agent.py` (lines 22-23, 36-42, 259-299, 316-343), `.../env/bot/Protoss_bot.py` (1986-2045 `on_step`, 2151-2154 `run_game(... realtime=args.real_time)`), `.../env/single_agent.py` (~219-226 wait loop), `.../test_the_env.py` (`--real_time` default False, line ~163). Underlying engine: burnysc2 6.2.0 (`requirements.txt`), `sc2/client.py:34` (`self.game_step: int = 4`), `sc2/main.py:198-204`.

1. **Clock**: paused/stepped in the default setting. `run_game(..., realtime=args.real_time)` with `--real_time` default `False` [code]. In `Protoss_bot.on_step` the bot blocks in `while self.transaction['action'] is None: time.sleep(0.001)` until the LLM side supplies an action, then executes it [code `Protoss_bot.py:~2000-2010`]; python-sc2 only calls `client.step()` after `on_step` returns when `realtime=False` [`main.py:198-204`]. Frames per env step: one env step = one `on_step` = python-sc2's default `game_step` of 4 game loops (burnysc2 6.2.0); I found no override in the repo (grep for `game_step` in `Protoss_bot.py` returned nothing), so ~4 loops = ~0.18 s of game time at 22.4 loops/s [derived; override in another file not excluded]. A `--real_time True` path exists and uses `RealTimeAgent` (`real_time_agent.py`, same logic with `action_window=20`) [code]; the paper reports a real-time human-vs-LLM test with a fine-tuned Qwen 1.8B on a home PC (Sec. 5.3) but gives no latency numbers.
2. **Action granularity**: a *named macro-action* from a fixed table (build pylon, train zealot, attack, scout, ...), each implemented by rule code `handle_action_{id}` in the bot (`Protoss_bot.py:~2020`). The bot also runs automatic behaviour every step (`await self.defend()`, `await self.distribute_workers()`; "attack when time >= 12:00 and supply >= 100") [code `Protoss_bot.py:1986-2030`]. The LLM's text is regex/similarity-parsed into K actions that go into an *action queue* [paper Sec. 4 "Action Extraction", Algorithm 1].
3. **Duration / interruption**: Chain of Summarization (CoS) = per-step single-frame summaries (rule-based by default) -> multi-frame summary over K steps -> CoT -> K queued actions; "updates actions every few frames" [paper Sec. 4]. Concretely in `chatgpt_agent.py`: the LLM is called when `current_step % action_interval == 0` with `action_interval=10`; its output is mixed with empty actions into an `action_window=10` queue at `action_mix_rate=0.5` (so ~5 real actions per 10 env steps, rest no-ops) [code lines 22-23, 260, 316-343; the comment says this "mitigates LLM compute pressure"]. So ~10 env steps x 4 loops ~= 40 game loops ~= 1.8 s of game time between LLM calls [derived]. No mid-queue interruption; reflexes live in `defend()`.
4. **Decisions / cost**: paper does not give calls per game. Win-rate table (e.g. GPT-3.5-turbo-16k 11/20, GPT-4-turbo 12/20 vs. built-in Harder AI) is the main result [paper Table 1]. Cost: UNVERIFIED (not reported).

## 4. OpenAI Five (Dota 2)

**Source**: OpenAI et al. 2019, *Dota 2 with Large Scale Deep RL*, https://arxiv.org/abs/1912.06680 : Sec. 2 (long horizons), Sec. 3.1 "Playing Dota using AI", Sec. 5 (human comparison: reaction time 217 ms), Appendix F (action space with *Delay*), Appendix L "Reaction time" with Figure 19, hyper-parameter table ("Frameskip 4").

1. **Clock**: real time, concurrent with inference (not paused). The engine runs at 30 frames/s; "OpenAI Five only acts on every 4th frame which we call a timestep", i.e. 7.5 observation+action pairs per second [Sec. 3.1, App. L]. To let game and model run concurrently they use an *action offset*: "we let the game engine carry on running until it produces an observation at time T+1 ... the action which the model takes at time T+1 is based upon the observation at time T" [App. L]. Net reaction time "randomly distributed between 5 and 8 frames (167ms to 267ms)", 217 ms on average [App. L, Sec. 5].
2. **Action granularity**: one primary discrete action per timestep (move / attack / cast / use item) + parameters: *Delay* (which of the 4 frames inside the frameskip to execute on, 4-dim), target-unit selection (189-dim) and 2-D offset (81-dim); average 8,000-80,000 legal actions per step [Sec. 2, App. F]. "In practice we found that the model did not learn to [use the delay] and simply taking the action at the start of the frameskip was better" [App. L]. Shopping, courier and skill-build order are hand-scripted [Sec. 3.1].
3. **Duration / interruption**: Dota orders (move-to, attack-target) keep executing in-engine until replaced; the policy re-decides every 4th frame (133 ms), so any new observation can override the order at the next timestep. Danger response is simply that fast re-decision rate plus the 5-8 frame reaction delay; no separate reflex mechanism is described.
4. **Decisions / cost**: ~45-minute games x 30 fps / 4 = "approximately 20,000 steps per episode" [Sec. 2]; rollout machines produce 7.5 steps/s and send data every 256 steps = 34 s of gameplay [Sec. 4]. Compute cost is reported in PFlops/s-days, not dollars (the rerun took 2 months, 150 PFlops/s-days).

## 5. VideoGameBench and VideoGameBench Lite (2025)

**Sources**: Zhang, Press, Yao et al. 2025, *VideoGameBench: Can Vision-Language Models complete popular video games?*, https://arxiv.org/abs/2505.18134 (Abstract; Sec. 2.5 "VideoGameBench Lite: giving agents time to think"; Sec. 3 "VG-Agent" and Lite paragraph; App. C.2 human interface; App. D.1-D.2 end-of-run criteria and cost). Repo https://github.com/alexzhang13/VideoGameBench : `main.py` (args, ~lines 38-40, 80-90), `src/vgbench_evaluator.py` (`run_episode_lite` 104-149, `run_episode_realtime` 151-206, `GBEvaluator.__init__` 77), `src/emulators/gba/interface.py` (`step`/`no_op`, 60-102), `src/emulators/dos/interface.py` (lines 16-52 Lite key delays, 54-130 actions, 131-190 `step`), `src/run_vgbench_gb.py:68`, README.

1. **Clock**: two settings, explicitly the "thinking-costs-game-time" vs "paused" contrast. **Full benchmark = real time**: "inference latency [is] a major limitation of frontier models in the real-time setting" [Abstract]; the README says model calls are "async with respect to the game". Code (Game Boy, PyBoy): while the LLM request is pending the evaluator keeps ticking the emulator with `no_op(1)` and `asyncio.sleep(0.01)` [`vgbench_evaluator.py:174-181`]. **Lite = paused**: "the underlying emulator is paused whenever the agent is processing information and deciding on its next action - the game only resumes momentarily when an action is made. This change effectively turns the real-time game into a turn-based interaction" [Sec. 2.5]. Code: Game Boy Lite never ticks during `await get_action()` (`run_episode_lite`); the DOS (js-dos in Chromium) Lite mode toggles `Alt+Pause` before and after each action (`dos/interface.py:50-51, 144-146, 182-183`). Lite set: Quake, Prince of Persia, Super Mario Land (dev), Doom II, Kirby's Dream Land, Zelda: Link's Awakening (test) [Sec. 2.5]. The paper's finding: "every model performs considerably better both quantitatively and qualitatively on VideoGameBench Lite" [Sec. 4].
2. **Action granularity**: low-level inputs, but a list per LLM call. Game Boy: the model replies with a list of buttons in an `actions` block; "each is performed for roughly 1/2 second or 30 frames" [prompt in App., "Instructions for Game Boy Games on VideoGameBench Lite"]. Code defaults differ: `GBEvaluator(action_frames=30)` (`vgbench_evaluator.py:77`) but the CLI default `--action-frames 15` (`main.py:~88`) is what `run_vgbench_gb.py` passes in, so which value the paper runs used is UNVERIFIED. Each button is held then released (`pyboy.send_input(release, delay=skip_frames)`, `gba/interface.py:96-102`). DOS/Windows games: `press_key` (default 0.1 s hold, `key_press_delay=0.1`), `hold_key(key, duration)`, mouse `click/move/drag`, `scroll`, `write` (`dos/interface.py:54-130`); paper: "each action lasts for a fraction of a second (e.g. "press_key A" presses the "A" key for 0.1 seconds)", the agent gets one frame 0.5 s after acting [Sec. 3, "VG-Agent"]. Observation in Lite: the latest frame for Game Boy, five past frames spaced 0.1 s for DOS [Sec. 3].
3. **Duration / interruption**: each action has a fixed short hold (0.1-0.5 s); there is no mid-action interruption. In real-time mode, game time that passes during inference is lost to the agent (stale actions) and the evaluator just keeps running with no-ops until the reply arrives; on a bad parse it no-ops for `action_frames` and retries [`vgbench_evaluator.py:184-192`]. The human baseline used the same restriction: sees only the most recent frame and the interface waits at least 0.5 s [App. C.2].
4. **Decisions / cost**: `--max-steps` default 15,000 [`main.py:40`]; runs are cut early if the screen is identical for >100 steps, or if the agent spends $30 (~2,000 steps) without reaching a new checkpoint; context window is 20 steps [App. D.1]. That implies about $0.015 per step [derived]. Reported per-run API cost (test split, App. D.2 Table 8), e.g. Civilization I: GPT-4o $14.46, Sonnet 3.7 $30.00, Gemini 2.5 Pro $5.29; Pokemon Crystal: $15.04 / $29.64 / $4.78; Doom II: $0.17 / $0.40 / $3.79. In the variance analysis of the best model (Gemini 2.5 Pro), the only game where any checkpoint is reached is Kirby's Dream Land (4.8% of the game) [App. D.3].

## 6. BALROG (NetHack, Crafter, MiniHack, BabyAI, TextWorld, Baba Is AI)

**Sources**: Paglieri et al. 2024/ICLR 2025, *BALROG: Benchmarking Agentic LLM and VLM Reasoning On Games*, https://arxiv.org/abs/2411.13543 (Sec. 3.1 "Evaluation setting", App. A-G per-game wrappers). Repo https://github.com/balrog-ai/BALROG : `balrog/config/config.yaml` (lines 4-6 history, 14-21 episodes/steps, 47-48 NLE, 54 MiniHack, 70 Crafter, 81 TextWorld), `balrog/evaluator.py:280-329` (episode loop), `balrog/environments/nle/auto_more.py`, `balrog/environments/crafter/crafter_env.py`.

1. **Clock**: strictly turn-based/lock-step, even for the real-time-ish ones. Each timestep the agent is prompted for one action string given its history, then `env.step(action)` [paper Sec. 3.1; `evaluator.py:308-318`: `for step in range(max_steps_per_episode): response = agent.act(obs, prev_action=action); action = env.check_action_validity(...); obs, reward, terminated, truncated, info = env.step(action)`]. One LLM call = one env step = one game turn/tick (NetHack keypress/command, one Crafter tick, one grid move). Crafter's monsters/day-night run on the same stepped clock. Baba Is AI has an explicit `idle: wait for one step` action [App. D prompt].
2. **Action granularity**: one primitive action from a small text vocabulary per call (move/turn/pick up/ "go forward", `place stone`, NetHack commands). Invalid output: the framework tells the agent the action was invalid, executes a fallback default (e.g. do-nothing or "north") and logs it [Sec. 3.1]. NLE wrapper `AutoMore` auto-presses `MORE` while the screen shows `--More--`, so one agent action may consume several raw keypresses of pure UI [`auto_more.py:18-33`]. Whether BALROG's NetHack vocabulary includes multi-turn commands (travel, counted search) is UNVERIFIED.
3. **Duration / interruption**: no durations; each action completes in the engine before the next prompt. Hazards are handled only by the agent choosing a new action the next step. Observation history window: 16 text observations, 0 images by default (`config.yaml: max_text_history 16, max_image_history 0`) [also paper Sec. 3.3 "history length of 16"].
4. **Decisions / cost**: per-episode caps (config): NLE 100,000 steps with a 150-step `no_progress_timeout`; Crafter 2,000; MiniHack 100; TextWorld 80 (prompt says "You have 80 steps"); default episodes: NLE 5, MiniHack 5/task, BabyAI 10/task, Crafter 10, Baba Is AI 3/task, TextWorld 10/task. The paper gives no dollar figure; it says naive few-shot prompting with full game demonstrations "is extremely computationally expensive" ("a single demonstration of NetHack game-play can require upwards of 700,000 input tokens") and that the o1-preview-class model was evaluated "exclusively on the NetHack environment due to budget constraints" [Sec. 4 discussion and Sec. 3]; a dollar figure per run: UNVERIFIED.

## 7. Factorio Learning Environment (FLE, 2025)

**Sources**: Hopkins et al. 2025, *Factorio Learning Environment*, https://arxiv.org/abs/2503.09617 (Sec. 2.2 "Environment Interface", 2.4 implementation, Sec. 3.1 settings, App. B "Experimental Costs" Table 3, App. D sleep tool and "no artificial rate limiting"). Repo https://github.com/JackHopkins/factorio-learning-environment : `fle/env/gym_env/environment.py` (231-240 `pause_after_action=True`, 436 `set_speed_and_unpause`, 519-521 `pause()` after the action), `fle/env/instance.py` (46 `reset_speed: float = 10`, 66-122 pause/speed control, 124-135 `get_elapsed_ticks`, 189-206 `fast=True`, 421-436 `eval_with_error(timeout=60)`), `fle/env/tools/agent/sleep/{server.lua,client.py}`, `.../craft_item/server.lua:5-9,161-168`, `.../move_to/server.lua:171`, `.../move_to/client.py:54-100`, `.../harvest_resource/server.lua:2-4,368-404`, `fle/env/mods/initialise.lua:25-32`.

1. **Clock**: *run only while the agent's program executes, paused between steps.* The gym env `step()` first calls `instance.set_speed_and_unpause(self.instance_speed)` (`environment.py:436`), runs the agent's Python, and finally "pause the game until the next step if this is part of a trajectory" (`pause_after_action` default True; `environment.py:519-521`). The server speed defaults to 10x (`reset_speed=10`, `instance.py:46,197`). Ticks per step are variable, not fixed: in the default `fast=True` mode the player is teleported and each tool adds a virtual cost to `storage.elapsed_ticks` (60 ticks = 1 s): crafting `energy_required x 60` per craft (`craft_item/server.lua:5-9`), mining time (`harvest_resource/server.lua:2-4`), walking via `calculate_movement_ticks` (`move_to/server.lua:171`), `sleep(seconds)` adds `seconds x 60` (`sleep/server.lua`). The Python client then really sleeps `ticks_added / 60 / game_speed` seconds (`sleep/client.py`, `move_to/client.py:72-80`) so the live factory keeps producing for the elapsed game time. With `fast=False` movement is animated and the client polls the walking queue every 0.5 s (`move_to/client.py:~96-104`). The paper: commands to the server come "with associated time penalties", and results include "in-game wall-clock time" [Fig. 2 caption, Sec. 2.4]. An environment step is "a single submission to the Factorio server, which returns the stdout, stderr, rewards and in-game wall-clock time" [paper, text beside Fig. 4].
2. **Action granularity**: model-written Python programs in a REPL with a persistent namespace; 13 action methods (`place_entity`, `move_to`, `craft_item`, `connect_entities`, `harvest_resource`, `insert_item`, `sleep` ...) and 10 observation methods [Sec. 2.2]. Agents observe only stdout/stderr, so they `print()` what they need.
3. **Duration / interruption**: a program runs to completion, to an exception, or until killed: "Programs that take too long to execute are terminated, to prevent runaway control flows (e.g. while True)" [Sec. 2.2]; the instance evaluation timeout default is 60 s (`instance.py:421-436`). `sleep` is capped at 15 s per call (tool docstring) and the paper says "We impose no artificial rate limiting on API calls ... the sleep method allows agents to implement deliberate timing" [App. D]. No mid-program interruption by events; `FactorioInstance(peaceful=True)` is the default so there are no enemy attacks (`instance.py:~192`). Python `assert` statements are the agent's own way to detect that the world differs from what it expected.
4. **Decisions / cost**: Lab-play: "Each task runs a trajectory of 128 API calls" with a 60 s in-game throughput hold-out measured after every step; Open-play: max trajectory length 5,000 steps, 8 independent runs per agent; memory = last 32 steps verbatim, older steps summarised into a 1,024-token report [Sec. 3]. Table 3 token/cost totals: Claude 3.5 Sonnet $502.62 (151M input / 3.2M output tokens), GPT-4o $402.06, Llama-3.3-70B $75.78, GPT-4o-mini $19.20, "Lab (all)" $318.62, total $1,318.28 [App. B]. Which table rows map to which settings is not stated in the text I extracted; the 1.3 cents/step figure in Sec. 0 divides $502.62 by 8 x 5,000 steps and is approximate [derived].

## 8. Claude Plays Pokemon / Gemini Plays Pokemon (and other "X Plays Pokemon" harnesses)

**Sources**:
- Public starter harness (the only Claude-side source code): https://github.com/davidhershey/ClaudePlaysPokemonStarter : `agent/emulator.py:29-32,56-82`, `agent/simple_agent.py:48-95,116-216,218-300,307-382`, `config.py` (`USE_NAVIGATOR = False`), `agent/emulator.py:331-485` `find_path`.
- Official stream harness details: not public. `[secondary]` Bradshaw, *So how well is Claude playing Pokemon?*, LessWrong 2025-03 (https://www.lesswrong.com/posts/HyD3khBjnBhvsp8Gb/so-how-well-is-claude-playing-pokemon): "Each 'action' is a full Thinking analysis ... followed by a decision to send some kind of input"; Run #2 abandoned at 35,000 actions; ~10,000 actions ~ 40 working hours; scaffolding includes a knowledge base, a critic Claude, and "a variety of tools to help it interact with the game".
- Gemini side: Gemini 2.5 technical report https://arxiv.org/abs/2507.06261 Sec. 4.1 and App. 8.2 "Gemini Plays Pokemon Additional Details" (Fig. 14, Fig. 15 discussion).
- Cross-system comparison + clock claim: *The PokeAgent Challenge* https://arxiv.org/abs/2603.15563 (Sec. 4.1, Fig. 7 caption, App. "execution model" paragraph, Table 2).

1. **Clock**: paused between actions, by construction. Starter code: the PyBoy emulator is only advanced by explicit `tick(frames)` calls inside the tool handler (`emulator.py:29-32`), so nothing moves while Claude generates its reply. The PokeAgent paper states the general fact, with citation to the community harnesses: "The 'X Plays Pokemon' systems all freeze the emulator between actions, giving the model unlimited deliberation time per step - wall-clock runtimes of hundreds of hours are common (e.g. Gemini's 406-hour playthrough ...). None penalize slow inference in their reported metrics" [`[secondary]` PokeAgent App., "execution model"; Table 2 marks the Claude/GPT/Gemini harnesses as community-built, not official]. Frames per action in the starter: for each button, hold 10 frames (`tick(10)`), release, then `tick(120)` if `wait=True` (default) else `tick(10)`; so 130 frames (~2.2 s of game time at 60 fps) or 20 frames per button, and several buttons may be sent in one call (`emulator.py:70-80`) [code; derived seconds]. The official Claude and Gemini harness frame counts: UNVERIFIED.
2. **Action granularity**: Starter tools: (a) `press_buttons(buttons: list, wait: bool)` over {a, b, start, select, up, down, left, right}; (b) optional `navigate_to(row, col)` ("Automatically navigate to a position on the map grid. The screen is divided into a 9x10 grid ... only available in the overworld"), implemented by a BFS/A*-style `find_path` over the screen-grid collision map and then replaying the path one `press_buttons([dir], True)` at a time (`simple_agent.py:75-92,162-171`; disabled by default via `USE_NAVIGATOR=False`). State fed to the model each step: a screenshot (upscaled) plus RAM-derived text (position, party, dialog) [`simple_agent.py:133-160`]. Gemini (GPP): button-press sequences; RAM subset overlaid on the screenshot; fog-of-war XML map with a visited counter per tile; two *agentic tools* that are themselves prompted Gemini instances, `pathfinder` and `boulder_puzzle_strategist` [Gemini 2.5 report App. 8.2, Fig. 14]; the developer plans "tool-creation tools". PokeAgent's own Table 2 summarises: Claude Plays Pokemon = pathfinder + knowledge base; GPT Plays Pokemon = button inputs + self-built minimap; Gemini Plays Pokemon = self-generated tools, code exec, pathfinder agent [`[secondary]`, Table 2].
3. **Duration / interruption**: a tool call is ballistic. In the starter, `navigate_to` loops over the planned path with no checks between steps (`simple_agent.py:167-170`), so a wild-battle encounter or dialog does not stop it (the next screenshot just shows it). There is no real-time danger because the game is frozen between calls. Session length is handled by summarising: when `len(message_history) >= max_history` (60) the agent asks Claude for a "CONVERSATION HISTORY SUMMARY" which replaces the history (`simple_agent.py:288-290,307-382`). Gemini GPP: action history in context; summary cleared every 100 turns; summaries re-compressed every 1,000 turns; a second "Guidance Gemini" critiques the main agent every 25 turns; primary/secondary/tertiary goals plus contingency goals [report App. 8.2]. Claude official: file-based knowledge base + critic [`[secondary]` LessWrong]; Opus 4 writes its own 'memory files' (e.g. a 'Navigation Guide') [Anthropic Claude 4 announcement, https://www.anthropic.com/news/claude-4].
4. **Decisions / cost**: Claude run #2: 35,000 "actions" [`[secondary]` LessWrong]. Gemini 2.5 Pro: first full playthrough 813 hours (Mar 28 - May 2, 2025), the second run with the finalized harness 406.5 hours [report Sec. 4.1]; the report plots actions-to-milestone (Fig. 15) but the action counts are not extracted: UNVERIFIED. Dollar cost per run: UNVERIFIED (not published in the sources read). For contrast the PokeAgent Speedrunning Track runs the emulator *in real time*: "Unlike most game benchmarks that pause between actions, our environment runs in real time - the game world continues while the agent reasons, making inference latency a first-class cost", and ranks teams by wall-clock time as well as steps (the fewest-step team needed 649 steps but ranked 5th by time; the RL-distilled Heatz policy needed 1,608 steps yet "executes far faster per step") [PokeAgent Fig. 7 caption and text].

## 9. Cradle (BAAI; general computer control; RDR2, Stardew Valley, Dealer's Life 2, Cities: Skylines, software apps)

**Sources**: Tan et al. 2024, *Cradle: Empowering Foundation Agents Towards General Computer Control*, https://arxiv.org/abs/2403.03186 (Sec. 3.1 Environment IO and Fig. 4/5, Sec. 4.1 implementation details, App. A Table 7 action space, App. B.3 RDR2 implementation "Game Pause", App. C.3 Stardew "Game Pause"). Repo https://github.com/BAAI-Agents/Cradle : `cradle/environment/rdr2/ui_control.py:25-50` (`pause_game`/`unpause_game`), `cradle/gameio/io_env.py:217-250` (`handle_hold_in_pause`/`handle_hold_in_unpause`), `cradle/module/executor.py:21,47,88-91`, `cradle/environment/rdr2/composite_skills/follow.py` (`MAX_FOLLOW_ITERATIONS = 40`).

1. **Clock**: paused for the real-time games, free-running for the rest. Paper Sec. 4.1: "due to the dynamism of the RDR2 and Stardew Valley and the LMM inference and communication latency, we must pause those game environments while waiting for backbone model responses. Other environments execute continuously." RDR2 pause mechanism: "after the agent finishes executing outputted actions, esc will be automatically pressed to pause the game and when the agent determines the next action, esc will be automatically pressed again to unpause ... there will be an animation lasting up to 0.5 seconds for both pausing and unpausing. During this animation, we can not control the character, but the dynamics of the game world keep changing, e.g., the wolves are still moving. It introduces additional challenges for the tasks that require precise timing, like combat" [paper App. B.3]. The time between two consecutive actions "can be as long as one minute" [same]. Stardew: the game pauses when its window loses focus, so after executing, Cradle activates another window [App. C.3]. Frames per step: not frame-based. The observation is a video clip of the last action recorded at 2 fps (a screenshot every 0.5 s); executed duration is whatever the generated skill specifies [Sec. 4.1 and App. A "Observation Space"].
2. **Action granularity**: the model writes or selects *code skills* (Python functions wrapping keyboard/mouse), instantiated with parameters such as duration, position and speed; e.g. `move_forward(duration)` = `press_key('W', duration)` [Sec. 3.1, Fig. 5]. Low-level action space (Table 7): key press/hold/release with duration, key combo and hotkey with sync/async wait, text type, mouse click/hold/move (with speed and tween), scroll, wait/noop. RDR2 composite skills are closed-loop CV controllers: `follow()` follows the minimap circle for `MAX_FOLLOW_ITERATIONS = 40` iterations in the repo (default 20 iterations per the paper) so that one LLM call covers many control ticks "to control both cost and time budgets" [paper App. B.3; `follow.py`]. A pre-defined `fight()` wraps multi-punch sequences because "the agent will only take one action per step [which] may not be high enough frequency to defeat an opponent. In order to allow sub-second punches, we provide a pre-defined action" [App. B.3].
3. **Duration / interruption**: skills with a duration run for that duration; "some actions require prolonged durations, such as holding down specific keys, which can coexist or interfere with other actions decided by subsequent decisions. Consequently, the reflection module must also decide whether an ongoing action should continue to be executed" [App. B.3, Self-Reflection]; asynchronous key actions are therefore allowed to overlap decisions. Across a pause, Cradle releases all held keys/buttons (`handle_hold_in_pause` calls `key_up` for each held key and saves a backup list) and re-presses them on unpause (`handle_hold_in_unpause`), so a held input survives the LLM thinking gap [`io_env.py:217-250`, `ui_control.py:25-45`]. `follow.py` breaks out of its loop when the on-screen text changes (`config.ocr_different_previous_text`), the one concrete event-based pre-emption found in this survey. Combat latency remains an acknowledged failure mode: "the high latency of GPT-4o's responses also makes it harder for an agent to deal with time-sensitive events, e.g., during combat" [App. B.2].
4. **Decisions / cost**: step caps: RDR2 500 steps per task; Stardew Valley 100; Cities: Skylines 1,000 (or until the budget is used up); software apps 30; Dealer's Life 2 is one in-game week [Fig. 7-11 captions, Table 6]. Each step is a multi-module GPT-4o pipeline (information gathering, self-reflection, task inference, skill curation, action planning; plus episodic-memory summarisation each iteration), so LLM calls per step is >1 but the exact count: UNVERIFIED. Dollar cost: not reported in what I read (the paper only mentions controlling "cost and time budgets").

## 10. Other systems that bear directly on "thinking costs game time" (if-time-allows items)

### 10.1 Orak (Krafton et al., ICLR 2026) - https://arxiv.org/abs/2506.03610
- **Clock**: 12 games; "Street Fighter III, Super Mario, and StarCraft II inherently require real-time gaming ... However, in our current evaluation setup, the game is paused during LLM inference to remove the impact of real-time constraints" [Discussion]. Stardew: "the game is paused to prevent in-game time from progressing" [App. J.4]; Slay the Spire: "not paused ... as the game state does not change over time" [App. L.4]. Per-game caps: SF3 10,000 steps (App. C.4), Super Mario 100 (D.4), Stardew 150, StarCraft II 1,000 (K.4), Slay the Spire 200 (L.4).
- **Granularity**: SF3 uses high-level actions that map to a predefined sequence of low-level frame inputs (Diambra native space is per-frame; "Move Closer" issues Right commands over four frames) [App. C]. Super Mario: each action spans 4 game frames (frame skipping) giving 7 discrete jump levels [App. D]. StarCraft II: high-level macro-actions.
- **Real-time experiment (Sec. 5.7, Table 8b)**: StarCraft II switched from paused to real time (LLM latency per step: GPT-4o-mini 19.6 s, GPT-4o 27.2 s, Gemini-2.5-pro 99.2 s with the reflection-planning agent): Hard level: every model drops from 75-100 to 0; Easy level: only GPT-4o keeps 100, the others drop to 0.
- **Async multi-agent design** (App. P.1): frame-by-frame orchestrator; each agent re-enters the decision loop "as soon as an agent completes its current action", actions last variable frame counts (e.g. "Move Away" 4 frames, "Super Attack" 7 frames), so actions overlap in the simulation.

### 10.2 Real-Time Reasoning Gym / AgileThinker (Stanford, Nov 2025) - https://arxiv.org/abs/2511.04898 , https://github.com/SALT-NLP/RealtimeGym
- Closest published design to "thinking costs game time" that is *reproducible*: instead of wall-clock they use **token count as the time proxy**: decoding time T = N_T x TPOT, and "the environment step[s] every N_TE ... tokens generated by agents"; time pressure levels 32k / 16k / 8k / 4k tokens per environment step. "If no action is produced in time, a default action is applied" (Freeway/Snake: keep the same direction; Overcooked: idle) [Sec. 2, Fig. 2 pseudocode `agent.think(timeout=T_E)`; `action = agent.act() or DEFAULT_ACTION`].
- Two paradigms: **reactive** (one action per env step, token-budgeted, budget forcing) vs **planning** (multi-step action lists or code plans executed until the agent finishes re-planning); AgileThinker runs both in two parallel threads, time-shared. Games run 100 steps (Overcooked M=100), 8 game seeds x 4 sampling seeds [Sec. 3-4, App.].

### 10.3 PokeAgent Challenge Speedrunning Track (2026) - https://arxiv.org/abs/2603.15563
- Pokemon Emerald, 15 milestones, emulator runs "at a fixed frame rate" continuously; agents get frames plus limited state and use MCP tools (`get_game_state`, `press_buttons`, `navigate_to` with A*) [Sec. 4.1, App. MCP Tools]. Wall-clock time and step counts are both reported; six teams completed all 15 milestones (Fig. 7 x-axis spans about 4 h); fewest steps 649 (Deepest, 5th by time) vs 1,608 steps for the RL-distilled Heatz policy, which "executes far faster per step" [Fig. 7 and text].

### 10.4 Street Fighter latency (FPX / "Win Fast or Lose Slow") - https://arxiv.org/abs/2505.19481
- Real-time Street Fighter on DIAMBRA with local models; "agents with just a 20% reduction in response time consistently outperform their slower counterparts"; the game itself caps the useful rate: "each character action takes a fixed amount of in-game time ... around 5 actions per second (i.e., 200 ms per action). Any optimization that reduces model latency beyond this threshold yields no further benefit" [Sec. 3.3, 5.3]. Also HFTBench (1-second market ticks; faster responders get better execution prices).

### 10.5 Balatro (BalatroBot / BalatroLLM / BalatroBench) - https://github.com/coder/balatrobot , https://github.com/coder/balatrollm , https://github.com/coder/balatrobench
- Turn-based card game exposed as a JSON-RPC 2.0 HTTP API with an explicit state machine: each method has a "Required State" (`MENU`, `BLIND_SELECT`, `SELECTING_HAND`, `SHOP`, `ROUND_EVAL`, `SMODS_BOOSTER_OPENED`, ...) and returns the new GameState [`docs/api.md`]. So the clock is the agent's own call; no real-time element. Calls per run, cost per run, and animation/wait handling: UNVERIFIED (BalatroBench publishes run artifacts on Kaggle, not read). Not used further.
